## Почему четыре отдельных сервиса, а не монолит

Систему можно было бы реализовать одним процессом на FastAPI с прямым
доступом к БД и Elo-расчётом внутри того же кода. Решение разделить её на
четыре независимых сервиса, общающихся по сети, принято по трём причинам:

1. **Требование курса явно разделяет «бэкенд» и «модуль взаимодействия с
   БД» как разные логические компоненты** (п. 2.2 и 2.4 задания), и требует
   отдельно взаимодействия backend → DB-модуль по сети (п. 2.4c) и
   backend → функциональный модуль (п. 2.4d). Монолит эти требования не
   демонстрирует явно.
2. **Разные задачи — разные языки.** Расчёт рейтинга — чисто
   вычислительная, CPU-bound задача без ввода-вывода; веб-слой (авторизация,
   маршрутизация, интеграция с внешним API) — I/O-bound задача. Разделение
   позволяет использовать для каждой задачи язык, для неё подходящий (см.
   ниже), а не подгонять одну технологию под обе.
3. **Изоляция сбоев и независимое масштабирование.** Если внешний OpenDota
   API станет недоступен или медленным, это не должно останавливать уже
   работающий расчёт прогнозов по уже загруженным данным — сервисы общаются
   по HTTP с таймаутами и не разделяют процесс.

## Обоснование выбора языков

### Frontend — TypeScript (React)

Из списка примеров курса. Статическая типизация ловит на этапе сборки
несовпадения структуры ответов бэкенда (например, переименование поля в
JSON) — что заметно уменьшает число ошибок в приложении, где фронтенд
общается с бэкендом, у которого есть собственная эволюционирующая схема
данных (команды, матчи, прогнозы, JWT-токены разных «областей действия»).

### Бэкенд и DB-модуль — Python (FastAPI)

Выбран из списка примеров курса. Причины:

- нативная поддержка `async`/`await` в связке с ASGI (Uvicorn) — то, что
  прямо требуется п. 2.4b задания для оркестрации сетевых вызовов без
  блокировки;
- Pydantic даёт автоматическую валидацию входных данных и генерацию
  OpenAPI-схемы, что ускоряет разработку нескольких HTTP-сервисов с
  общими контрактами (`backend` и `db-service` обмениваются JSON по
  фиксированным схемам);
- `pyotp` и `pyjwt` — готовые, проверяемые временем реализации TOTP
  (RFC 6238) и JWT (RFC 7519), не требующие писать криптографию вручную.

**Отдельное инженерное решение:** `db-service` использует не асинхронный,
а синхронный SQLAlchemy, обёрнутый в синхронные (`def`, не `async def`)
эндпоинты FastAPI — Starlette в этом случае сама выполняет их в пуле
потоков. Причина: асинхронный режим SQLAlchemy 2.0 зависит от
C-расширения `greenlet`, чей предсобранный wheel не загружается на
используемой в разработке версии Python (см. `db-service/app/database.py`
— там же зафиксирован сам факт и причина решения). Синхронный SQLAlchemy +
пул потоков — стандартный, документированный FastAPI способ работать с
блокирующим драйвером БД, не уступающий по корректности при том уровне
нагрузки, который характерен для учебного проекта.

### Функциональный модуль — Go

Расчёт Elo-рейтинга и вероятности победы изначально писался на Rust, но
был перенесён на Go в процессе разработки (после того как на используемой
машине не удалось быстро настроить компоновщик MSVC, необходимый
стандартному Rust-таргету на Windows). Итоговый выбор Go, тем не менее,
обоснован независимо от этого инцидента:

- Go есть в списке примеров курса для функциональных модулей;
- расчёт «формы» команды по последним матчам — задача, естественно
  распараллеливаемая по командам, и модель конкурентности Go (горутины +
  каналы) выражает это распараллеливание короче и нагляднее, чем ручное
  управление пулом потоков;
- отдельный бинарник Go со встроенным HTTP-сервером (`net/http`) не
  требует внешнего рантайма при развёртывании — важно для контейнеризации
  (`prediction-engine/Dockerfile` — минимальный `alpine`-образ).

Реализация сознательно разделяет две части расчёта на разные модели
выполнения: обновление Elo-рейтинга **последовательно** проходит по
матчам, отсортированным по времени (каждый следующий матч команды зависит
от результата предыдущего — это неотъемлемо последовательная операция), а
расчёт «формы» команды выполняется **параллельно**, пулом горутин по числу
ядер CPU, — так как истории разных команд независимы друг от друга.

## Сетевое взаимодействие

Все компоненты общаются по HTTP/JSON:

```
frontend → backend            (REST, JWT в заголовке Authorization)
backend  → db-service          (REST, backend/app/network/db_client.py)
backend  → prediction-engine   (REST, backend/app/network/prediction_client.py)
backend  → OpenDota API        (REST, внешний источник данных, backend/app/ingestion.py)
```

Формат JSON и разбиение на короткие, независимые HTTP-эндпоинты выбраны
вместо, например, обмена сообщениями через очередь — для учебного проекта
такого масштаба это избыточное усложнение, не дающее выигрыша ни в
надёжности, ни в демонстрации требуемых архитектурных возможностей
(асинхронность и так демонстрируется на уровне `async`/`await` и
горутин, а не на уровне транспорта).
